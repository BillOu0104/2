# 独立100000年确认预注册（V1）

在接触确认Seed积分前冻结。探索依据见EXPLORATION100K_RESULTS.md、WEAK30_RESULTS.md和ROBUSTNESS_PROTOCOL.md。V2-E的16种子只用于探索，不进入本队列。

## 队列、候选与数值方法

- 主确认Seed固定为V2-CONFIRM-20261021-0..127，128个全新连续编号。只检查初值字节唯一性及与既往队列不重合，不预模拟寿命、不筛掉困难初值、不按Seed调参。
- 两个预定候选：deflect4-trigger8和reflect-trigger8；另有newton及legacy-cage匹配基准。所有配置沿用7f64a8a已实测原型，没有新的动力算法或参数调优。
- 每次真正积分100000显示年；60帧/年、.0075求解器单位/帧，最大步长.00075、eta .0075。至少60000000名义子步，不加速显示时间代替计算。成熟窗口固定[10000,100000]。
- 预定前32个确认Seed额外运行两候选的dt/eta减半组（__h2），最大步长.000375、eta .00375。它们是数值敏感性辅助组，不替换主确认，不选择较好精度结果冒充主组。每组32个匹配Seed，同初值，至少120000000名义子步。
- 16个批次，每批连续8Seed；前四批6个profile，后十二批4个profile，共576条完整预定结局。小批只为保存/恢复，所有主组仍是同一128Seed队列，不拼接不同种子时间或当成16份独立研究。
- P5行星重生、真实半径、纪元逻辑、控制预算、恒星接触与动力学确认分离判据均沿用冻结源码。行星/文明与三星完整性分开；不存在整宇宙重置。

## 主要评价

1. A：每个候选100000年三星完整率。目标参考线70%和80%都报告，提供Wilson95%区间，不用点估计代替不确定性。
2. C：沿用已冻结诊断：完整运行、成熟条件FTLE>0.003/年、成熟紧双星身份交换>=20、最长连续动力学层级<1000年。FTLE给定主轨迹行星生命周期，不是完整四体无限时间指数。
3. 连续参与：在正式确认之前，将探索期公开的几何提醒另冻结为更严格的联合证据终点：在上述C基础上，全窗最长几何隔离<=5000年且成熟非层级占比>=10%。旧诊断与此较严格终点都报告，不回写探索旧分数；阈值不是数学混沌定理。未满足只能说证据不足，不等于证明周期。
4. B：全窗与成熟恒纪元，分别给所有Seed、物理幸存者、以及上述联合证据子集的统计，明确不同分母。目标10%–15%不是上限，不压低超出值。每Seed原值、分位数、均值和Seed层级bootstrap95%区间一并给出。
5. D：累计有符号/绝对功、总额外冲量、峰值/平均/RMS加速度、分量及事件净速度跳变、激活帧/连续作用时间、动量与角动量净及可恢复的累计改变量。行星再生外部预算独立列出；净功或净动量接近0不表示无干预。

两个候选是共同预定的比较对象，不从确认Seed中再调参。除普通Wilson95%外，A和较严格联合终点的两个候选共四个比例，另给Bonferroni调整的Clopper–Pearson区间，说明多重比较。最终选择综合混沌/连续参与、完整率、成熟恒纪元和控制代价；不以单一存活率或事后有利权重选“最优”。若都不满足，保留该确认失败结果，再用新探索/新确认队列研究，不能重用本队列冒充新的独立确认。

所有失败、行星损失/重生及文明结局保留；提前恒星失败后的恒纪元按预定全窗分母记0。数值UNKNOWN单列，不能当作物理死亡或成功。未完成批次为pending，不加入失败数，也不能称完成128Seed。任何数值UNKNOWN或版本/哈希/初值审计不通过，保存阶段后停止升级并分析。

## 数值证据的边界

探索30k将dt/eta减半后，两候选各8/8完整，能量残差明显下降，但成熟恒纪元匹配均值仍有约6–8个百分点变化；8Seed不足以证明统计收敛。正式前32Seed的辅助精度组用于继续量化此不确定性。不能仅凭能量残差小宣称长期混沌统计精确；即使主确认达到目标，也须完成数值/兼容性综合评审才考虑正式集成。

影子幅度1e-7/1e-9及5/20年窗口探索32条保持主轨迹/控制/计数逐位不变，FTLE诊断对少量参与不足样本仍不通过；不挑幅度提高分数。无重生消融的成熟恒纪元为0，说明B依赖文明行星持续存在的P5协议；P5损失频率、缺席、重生后固定25年贡献必须独立报告，不能隐藏。

## 保存和恢复

study文件confirmation-v1/study.json和16个批次配置在首条积分前提交。results/confirmation-v1.manifest.json冻结科学源码、二进制、驱动、初值审计和全部配置哈希。源码保持7f64a8a；不改main或正式UI。

run-confirmation.py使用已有run-stream.py，每次只运行同批两Shard，总计2CPU。每批审计、聚合去重、Git检查点、records归档/check和推送，再进入下一批。源/配置/二进制不匹配或UNKNOWN会停止；推送失败单列，不把本地提交说成已推送。恢复前依STATUS核对锁、worker与最近20分钟记录；恢复跳过已完成键，不混写不同参数或代码。

完整主确认、数值敏感性、功能/UI兼容性与回滚保存均充分后，才进入集成分支；覆盖main仍须用户最终验收。
